The Argument

Calling Supabase "Jade's brain" conflates storage with cognition. A database does not think. An LLM thinks but has no memory. Agent code takes action but can't reason without an LLM.

"Every large language model resets between sessions — there is no built-in persistence, no recall of prior interactions, and no accumulated knowledge from previous agent runs. This statelessness is a design choice, not a flaw." — Atlan, "Memory Layer for AI Agents"

The Three Layers

01

Agent Runtime

The Body

  • Python code that runs agents
  • Routes work between specialists
  • Manages pipeline state
  • Calls tools, APIs, databases
  • Enforces guardrails & cost controls

Your code: CrafturaFlow, CrafturaCrew, Jade routing

02

LLM Processing

The Thinking Engine

  • Stateless reasoning via API
  • Analyzes, generates, decides
  • Each call is independent
  • No memory between calls
  • Rented compute intelligence

Your stack: GPT-4, Claude, Gemini, llama.cpp

03

Data & Memory

The Hard Drive (Supabase)

  • Persistent storage across sessions
  • Structured data with ACID guarantees
  • Identity, projects, conversations
  • Audit trails & references
  • Row-level security for access control

Your schema: brain_profile, brain_projects, brain_conversations

The "Brain" Terminology Problem

What's Said Why It's Wrong What's True
"Supabase is Jade's brain" A database doesn't think Supabase stores memory data
"Jade lives in Supabase" Code runs as a process, not in a DB Jade's runtime loads from Supabase
"The brain loads context" Databases don't load context Runtime calls load_brain()
"Brain functions think" SQL returns data, doesn't reason LLM reasons over loaded data
